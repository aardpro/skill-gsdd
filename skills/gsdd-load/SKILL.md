# GSDD 加载

为当前任务产出 SSOT 任务简报，并判定下一步——直接实现还是走 `/gsdd-change`。核心纪律：**索引先行、按需取段**，不为一个任务读整个 ssot/。没有 ssot/ 的项目 → 提示先跑 `/gsdd-init`。

## 三步取段法

1. **路由器**：全文读 `ssot/README.md`（它很小，且是唯一入口）。
2. **定位**：对 L0/L1/L2 各文件——
   - 文件 ≤ 300 行（README 头部可调此阈值）→ 可全文读。
   - 超过阈值 → **禁止全文**。用 grep 按编号/关键词命中索引行与小节标题，再按行号只取命中段落；需要浏览面时只读其 `## 索引` 段。
3. **取段**：只取任务相关条目的全文（验收项、术语口径、design 小节、剧本步骤）。

## 任务简报（默认 ≤2000 token，约 120 行；阈值在 ssot/README 头部可调）

以任务描述（args）为输入，简报只装六样：

1. 相关验收项**全文**（A 编号 + 原文）。
2. 涉及的术语唯一口径（只列术语与定义，不搬运 design 正文）。
3. 波及剧本的相关步骤（只列步骤与编号）。
4. 本任务禁止事项：不新增验收项/标准；规范缺口不自行弥补，路由交给第 6 条判定。
5. **改表/换库/迁移类任务附加**：`schema.md` 相关条目（S 号原文）、`stack.md` 涉及组件、`decisions.md` 相关 D 号；三者任一在简报中缺失 → 简报开头标红「数据事实不完整，先补加载再动手」。
6. **路由判定（简报最后一行，锁死二选一）**：「✅ 已覆盖 → 直接实现，交付前 `/gsdd-accept`」或「⛔ 有规范缺口 → 下一步 `/gsdd-change`」；后者必须附缺口清单（哪个需求没登记 R / 哪条验收没覆盖 / 哪个术语缺口径），提案采纳后重跑 `/gsdd-load` 再实现。判定依据是任务能否挂上现有 R/A 编号——不靠程序员记忆。部分覆盖则两行都写：✅ 部分可直接实现，⛔ 部分等 change 采纳后重跑本命令。

简报留在对话里，不落盘（ssot/ 与 evidence/ 都不放）。

## 超限处理（优先级锁死，溢出必须可见）

判定按**行数**执行——agent 数不了 token，但数得了行：简报超过 120 行（默认阈值，约 2000 token，以 `ssot/README.md` 头部声明为准）即超限。超限时压缩优先级锁死：

1. **不可压缩**：禁止事项、路由判定、数据事实（S 号原文、stack 涉及组件、D 号），一字不减。
2. **可降级**：验收项全文降为「A 编号 + 一行摘要 + 按需取段指引」——需要原文时按三步取段法回 `acceptance.md` 取。
3. **随后精简**：术语口径、剧本步骤按余量精简。

无论压到多少行，简报开头必须标红「简报超限，建议拆分任务」——溢出必须可见，永不允许静默。
